# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **prompt-engineering toolkit** (no application code) that turns reference images into on-style 2D mobile-game assets, in any art style the refs show (cute casual to dark/gritty/realistic). The deliverable is `studio_primer.md` — a self-contained mega-prompt the user pastes into a vision-capable LLM chat, which then answers short commands (`STYLE`, `LOAD`, `UPDATE:`, `ASSET:`, `CHARACTER:`, `BACKGROUND:`, `OBJECT:`, `CHECK`, `REGEN`, `TWEAK:`) to produce a `style_guide.yaml` and, from it, image prompts. The primer only ever outputs **text** — it never invokes an image tool even when the host chat has one.

**Draw-fresh only (deliberate design decision, 07/2026):** every asset is generated FRESH from the style_guide (eyedropper-verified hex pinned in the prompt) — that is the path generative models are good at. The former EXTRACT / UPSCALE / `STYLE: design system` board paths (re-rendering existing pixels) were removed after real-world testing showed them producing mushy, broken output on gpt-image; do not re-add "keep the source pixels" paths. The one image-edit path kept is the CHARACTER pose variation (identity lock). **The STYLE ref is attached only to `STYLE`** — later commands inherit the style_guide from context, and their attachment slot belongs to that command's own ref (TARGET layout / CHARACTER / the generated result for CHECK); don't reintroduce "re-attach the STYLE ref when generating" wording.

**Generator-neutral by design**: the toolkit stops at the prompt. It never generates images and must not be coupled to any specific image generator (gpt-image / Gemini "Nano Banana" / Midjourney are the user's choice). Scope is 2D assets in four classes: **UI/UX** (screens — including **in-game gameplay screens with HUD** — icons, buttons, panels, UI kits, icon/asset sheets), **backgrounds** (actor-free backdrops), **characters** (static art + pose variations via a CHARACTER ref), and **objects/props** (down to board-cell **game pieces**, `object_spec.size_class: game_piece`). Out of scope, stated in §0 point 6 and FINAL CONTRACT item 7: animation/sprite sheets of motion frames and standalone VFX — the primer says so and offers the nearest static path. Repo content stays in English (prompts target English-language generators).

## The one rule that matters: the primer is GENERATED

`studio_primer.md` is bundled from two source directories — never hand-edit it independently of them:

- `schema/` — field + enum definitions. `style_guide.schema.yaml` is canonical; `asset_spec.schema.yaml` / `layout_spec.schema.yaml` describe the optional structured UI asset/layout inputs; `background_spec.schema.yaml` / `character_spec.schema.yaml` / `object_spec.schema.yaml` the optional structured inputs for the three non-UI classes.
- `style_tokens/` — the style dictionary mapping each enum to an English prompt phrase (`materials`, `render_shape`, `light_color`, `layout_negative`, `character_environment`, `ui_components`).

Change flow: edit the source file first → rebuild the affected primer section → verify against the **BUILD MANIFEST** in the primer's header comment (it lists every source section that must be present; grep each item). The schemas are documentation-style pseudo-YAML (fields + enums, not JSON Schema); there is no build/validator script — the repo intentionally stays code-free.

## Architecture (pipeline inside the primer)

STYLE ref image(s) → **§3 ANALYZER** → `style_guide.yaml` (enums from §1 only, plus per-dimension `confidence`; `<0.75` = user must review; hex values are estimates the user fixes via eyedropper + `UPDATE:`; the `character`/`environment` blocks are OPTIONAL — filled only when the refs actually contain characters/scenes, never guessed; §3 also ingests a full pasted guide via `LOAD` — validate vs §1, reject structural errors in one `LOAD ERRORS` block, adopt verbatim, reprint; the `presets/` files are pre-authored inputs for exactly that path) → **§4 SYNTHESIZER** (the four generate commands map 1:1 to its four prompt branches — `ASSET:`=UI, `CHARACTER:`, `BACKGROUND:`, `OBJECT:`; each branch translates every enum through the §2 dictionary, in its fixed prompt order ending with "Avoid:") → one natural-language prompt → user generates the image elsewhere → optional **§5 CHECKER** compares the generated image back against the style guide — extra-strict on palette hex (per-role expected vs observed) and UI edge sharpness (blur/mush/soft text = off) — and emits per-fix `TWEAK:` lines plus **ONE consolidated `TWEAK:`** the user copies to fix everything in one go.

Character **pose variation** is a sub-branch of §4: `CHARACTER:` + an attached CHARACTER ref (the already-generated character; or `character_spec.character_ref`) → an image-EDIT prompt that opens with the §2 identity-lock phrase (face/outfit/colors frozen, only pose/expression change). It is the ONE image-edit path in the toolkit — it needs an image-*editing* generator (the §4 IMAGE-EDIT PATH NOTE covers this). It does NOT re-describe the character or re-translate style dimensions — the prompt says "keep the lighting, outline and background treatment unchanged" and its "Avoid:" is the §2 **No-restyle set** + non-screen + character (or simplified) + always tails; it has its own shorter `# SELF-CHECK:` receipt (§4 rule 14).

Sub-modes stay inside their parent command — no new command, so §0/README stay 1:1. `ASSET:` has three (v2.3.0): the **UI-KIT sheet** (`asset_spec.kit` / `type: ui_kit`, or "UI kit" in text) — the whole UI component set drawn on ONE canvas in one pass; the **ASSET SHEET** (`asset_spec.sheet`: columns/rows/items — N×M matching single assets, closed item list in order, non-screen tail KEPT because every cell is a text-free single asset, screen-length budget); and the **GAMEPLAY SCENE / HUD** (`asset_spec.gameplay`: setting/actors/play_area/hud — an in-game screen = play area styled via the `environment`/`character` blocks + HUD chrome styled like any screen with COLOR/SHAPE LOCK per HUD surface; tails = always + "no additional HUD elements…" — **never** the background tail (actors are wanted) and **never** the non-screen tail (a HUD IS UI); it is the answer to "which command makes an in-game screen?" — `ASSET:`, never `BACKGROUND:`; §2 has a `### gameplay scene` group with the subject phrase + `hud_closed_list`). `CHARACTER:` has the **character sheet** (`character_spec.sheet`). The sheets lean on the §2 word **consistent** as the anti-drift anchor. `environment.depth: tile_grid` (board/tile-map levels) is a real schema enum since v2.3.0 (it had been token-only); `object_spec.size_class` has a §2 phrase per value (`### object size_class`). UI widget/text style itself lives in the OPTIONAL `typography` / `controls` style_guide blocks.

Distinctions that must not be blurred:

- **STYLE ref** ("how it looks" → style_guide) vs **TARGET ref** ("what to make / its layout" → asset content) vs **CHARACTER ref** ("who this is" → pose variation, identity locked). Different inputs to different commands/branches.
- `style_guide.background` (overall style background) vs `asset_spec.background` (popup/fullscreen/transparent/scene for one asset) vs the `background` asset CLASS (a scene made via background_spec).
- Negative tails: `negative_tail_always` is appended to every prompt; `negative_tail_non_screen` ("no text, no UI overlays") only to single assets — screens ARE UI, so it must be skipped there; `negative_tail_character` (anatomy) only to characters — BUT when `feature_exaggeration: high` (mitten/stump styles) use `negative_tail_character_simplified` INSTEAD ("no distinct fingers", Banana2 Zero-Digits — "no EXTRA fingers" is the wrong guard there); `negative_tail_background` (no actors) only to backgrounds.

## Consistency invariants (check after any change)

- Every enum in `schema/style_guide.schema.yaml` appears in primer §1; every token group in `style_tokens/*.yaml` appears in primer §2 (currently 41 `###` headings). Token groups that are deliberately NOT style_guide fields (free-form craft vocabulary the synthesizer may add, tagged `[AI-suggested]`): `form_proportions`, `color_treatment`, `lighting_extra`, the pixel-art `grid`/`outline_px`/`palette_cap` modifiers — §2 labels them "free-form craft note, not a style_guide field"; every OTHER token enum must exist in the schema (the reverse check below). Token phrases express ONLY their enum's meaning — no cross-dimension aesthetic adjectives (mood words live in mood tokens, proportions in shape/form tokens); the §4 context starter is SYNTHESIZED from `project.genre` + `platform` + `style.rendering`, never a hard-coded phrase, and `style_guide.negative` is ref-derived (§3 rule 5), never a stock list — these three rules are what keep the toolkit from biasing every ref toward one house style. Two enforcement self-checks back them up (added after a real-run compliance audit, 07/2026): §3's **Consistency check** (list discipline — only genre/mood/palette/color_map/background.color/negative are lists; no `negative` entry may contradict a filled field, e.g. dark background forbids `dark_theme`; color_map REQUIRED when the refs show UI; **shape re-measure** — slanted tabs ⇒ `shape.slant`, italic lettering ⇒ `italic_display`, corner size measured — and the negatives check states the bg hex + a dark/light call; both report OBSERVED-value slots in the `# CONSISTENCY:` receipt rather than rubber-stamp ✓s, because ✓-only receipt items let GPT-5.5 keep habit-defaulting rounded/medium and re-admitting `dark_theme` over a dark bg, 07/2026. When the receipt honestly reads `slant=none` on a slanted ref, that's a host VISION limit, not compliance — the remedy is the human `UPDATE:` override, same as eyedropper for hex) and §4 **rule 12** (prompts are flowing prose, self-contained — never referencing "the style guide" the generator can't see — with hex inline per surface, within the §6 word budget); the §0.5 rows repeat both so they aren't skipped. §4 rule 6 also carries a **contradiction guard** — at translation time it SKIPS any `negative` entry that contradicts a filled style_guide field (second gate for the same failure, since analyzer compliance is stochastic); and §4 rule 13 dedups **feature entry points** on self-suggested screen layouts (one feature = one entry point per screen; §5 checks it on generated screens); §5 itself is format-locked (binary ok/off table + TWEAK lines only, no scores/essays) and its rule 7 forbids art-director drift — a TWEAK may only pull the image TOWARD the style_guide, never away. Since silent self-checks proved unreliable in real runs, the primer has a **§0.6 OUTPUT GATE**: every answer is drafted → verified against its §0.5 row → revised until it passes → printed WITH a receipt line (`# CONSISTENCY:` opening the analyzer's REVIEW NOTES, `# SELF-CHECK:` closing every §4 ASSUMPTIONS block — now mandatory on every §4 answer, the fixed ok/off table for CHECK); receipts sit OUTSIDE the copyable prompt (the prompt the user copies to the generator never contains them). **Answer shape (v2.3.0, stated identically in §0.5, §0.6, §4 skeleton, §6 and FINAL CONTRACT item 4):** prompt → `# ASSUMPTIONS` (last line = `# SELF-CHECK:`) → the one-line §6 reminder; every receipt item is `✓` or `n-a — <reason>` (a fixed all-✓ string forced false ✓s on objects/backgrounds/pose variations); `UPDATE:` has its own `# CONSISTENCY: UPDATE` receipt with no re-measure slots (there is no image to re-look at); `REGEN`/`TWEAK:` cite §4 and reprint the full prompt; `CHECK` has a defined pass case (table + one pass line) and a no-image rule. **Word budget (§6) is per asset class and is outranked by rules 4/7/9/13** — a lock is never dropped to hit it; the receipt reads `word budget over — <which lock forced it>` instead (the old "hard limit" of 300–400 words could not physically hold a full COLOR LOCK, so hosts silently dropped hex). Each command section (§3/§4/§5) opens with an **OUTPUT SKELETON** ("your entire reply is exactly these blocks — no intro sentence, no extra sections") and the file ends with a **FINAL CONTRACT REMINDER** — the recency anchor restating the seven most-violated items; both were added after a strong host model (GPT-5.5) with the full primer still free-formed its replies. The OPTIONAL UI blocks `typography` and `controls` (toggle/slider/checkbox/progress, in `style_tokens/ui_components.yaml`) must appear in both §1 and §2 — they anchor UI-widget/text consistency the same way `material.button/container/icon` anchor button/panel/icon. Likewise the OPTIONAL `color_map` block (the **COLOR LOCK**, per-surface hex; tokens in `style_tokens/light_color.yaml`) must appear in §1, §2 (`### color lock`), §3 (analyzer fills it per surface, with scope notes), §4 (rule 4: contract sentence once + hex INLINE per surface + color-lock negatives in rule 6) and §5 (CHECK compares every filled surface) — it exists because text-only hex is followed loosely; per-surface inline hex is the strongest text-side color device. Its shape twin is the **SHAPE LOCK** (07/2026): OPTIONAL `shape.ui_panel_geometry` (panel/card/tab silhouette archetype; `slant` stays the skew degree) — when geometry/slant is filled, §4 ECHOES the silhouette phrase on every UI surface class (panels/cards/tabs/buttons/nav) instead of one global mention, appends the shape-lock negative for the chunky/slanted archetypes, and §5 flags any single pill-rounded surface as `off`; geometry phrases stay silhouette-only (no corner/camera words — token purity), and the §3 receipt's `panel=` slot reports the observed archetype.
- The primer §0 command table and README's "Command reference" table must match 1:1 (currently `STYLE, LOAD, UPDATE:, ASSET:, CHARACTER:, BACKGROUND:, OBJECT:, CHECK, REGEN, TWEAK:`, in that order — `TWEAK:` carries the colon everywhere since v2.3.0, so the consolidated line `CHECK` prints is literally the command). The §0.5 EXECUTION CHECKLIST rows must cover the same commands as §0 (it's a per-command anti-miss contract, not a second command list).
- **Presets policy**: `presets/*.yaml` are pre-authored `style_guide.yaml` **DATA instances** (inputs for `LOAD`) — never sources for the primer build, and never a render path (don't frame them as boards or re-introduce extract/board language; the draw-fresh decision above stands). They contain **no `enum:` keys** (instances, not schemas — which keeps them out of the enum-coverage scan by construction); every enum-typed value must be valid per `schema/style_guide.schema.yaml` (the preset validator below enforces this); the §3 negative-contradiction and confidence↔block-pairing rules apply to them as if the analyzer had emitted them. Inspiration screenshots used to author a preset live only in the gitignored `presets/refs/` (same policy as `doc/`) — never commit them.
- The **IMAGE-EDIT PATH NOTE** lives once in §4, scoped to the pose-variation branch (the toolkit's only image-edit path) — don't duplicate it elsewhere when editing.
- **No "separate style reference" wording anywhere** (token `layout_reference_lock` or primer §2): the STYLE ref is attached once; the v2.3.0 pass removed a leftover `with_style_ref` clause that contradicted this — the verification grep below keeps it out.
- §4 has a **Rule 11 coverage self-check**: every filled style_guide dimension must be translated or explicitly `# [skipped]` in ASSUMPTIONS. The per-branch prompt orders name outline/mood/button.depth/icon.* explicitly — keep them named when editing the orders.

## Release flow

Toolkit releases are semver git tags + GitHub releases (independent of the `version: 1.0` *schema* version inside style_guide.yaml — that only changes on breaking schema changes). To release: (1) bump the `TOOLKIT vX.Y.Z` marker in the `studio_primer.md` header comment; (2) add the entry to `CHANGELOG.md`; (3) run the full verification below; (4) commit, tag `vX.Y.Z`, push, `gh release create vX.Y.Z` with the changelog entry as notes.

## Verification commands

```bash
# all YAML parses (needs PyYAML: pip3 install pyyaml)
python3 -c "import yaml, glob; [yaml.safe_load(open(f)) for f in glob.glob('schema/*.yaml') + glob.glob('style_tokens/*.yaml') + glob.glob('presets/*.yaml')]"
# fallback when PyYAML is unavailable (macOS system Ruby):
ruby -ryaml -e 'Dir.glob("{schema,style_tokens,presets}/*.yaml").each { |f| YAML.load(File.read(f)) }; puts "OK"'

# every underscore enum value in schema/*.yaml appears in the primer (scoped to values containing "_" —
# one-word enums like grid/none/center appear everywhere in prose, so grepping them would always false-pass)
ruby -e 'prim = File.read("studio_primer.md"); missing = Dir.glob("schema/*.yaml").flat_map { |f| File.read(f).scan(/enum: \[([^\]]*)\]/).flatten.flat_map { |l| l.split(",").map(&:strip) } }.uniq.select { |v| v.include?("_") }.reject { |v| prim.include?(v) }; if missing.empty? then puts "OK - all underscore enum values present in primer" else puts "MISSING: #{missing.join(", ")}"; exit 1 end'

# every preset is a valid style_guide instance: version line present + every enum-shaped scalar exists in
# schema/style_guide.schema.yaml's enums (negative entries and aspect_ratio are free-form and exempt;
# hex/floats/bools are self-exempt by type/pattern)
ruby -ryaml -e 'allowed = File.read("schema/style_guide.schema.yaml").scan(/enum: \[([^\]]*)\]/).flatten.flat_map { |l| l.split(",").map(&:strip) }.uniq; bad = []; check = lambda { |node, path| case node when Hash then node.each { |k, v| check.call(v, path + [k.to_s]) } when Array then node.each { |v| check.call(v, path) } when String then bad << "#{path.join(".")}: #{node}" if !path.include?("negative") && path.last != "aspect_ratio" && node =~ /\A[a-z0-9_]+\z/ && !allowed.include?(node) end }; Dir.glob("presets/*.yaml").each { |f| data = YAML.safe_load(File.read(f)); bad << "#{File.basename(f)}: missing version" unless data.is_a?(Hash) && data["version"]; check.call(data, [File.basename(f)]) }; if bad.empty? then puts "OK - presets valid vs schema enums" else puts "INVALID: #{bad.join(" | ")}"; exit 1 end'

# primer contains the BUILD MANIFEST items (spot-check; full list in the primer header) — any 0 is a broken build
for p in "version: 1.0" "asset sheet layout" "Always-append tail" "orthographic" "game art asset in {rendering-family} style" "chibi proportions" "identity lock" "layered_parallax" "size_class" "EXECUTION CHECKLIST" "IMAGE-EDIT PATH NOTE" "Coverage self-check" "UI-kit reference sheet" "color lock" "lighting.contrast" "realistic_painted" "Consistency check" "self-contained: NEVER" "duplicate feature entry points" "TOWARD the style_guide" "no additional UI elements" "OUTPUT GATE" "SELF-CHECK" "OUTPUT SKELETON" "FINAL CONTRACT REMINDER" "never free-form describe" "TOOLKIT v" "never a blind 9:16" "shape.slant" "shape re-measured" "ui_panel_geometry" "SHAPE LOCK" "LOAD" "adopted verbatim" "LOAD ERRORS" "GAMEPLAY SCENE" "ASSET SHEET" "game_piece" "tile_grid" "No-restyle set" "CONSISTENCY: UPDATE" "answer shape" "n-a — "; do printf "%s\t%s\n" "$(grep -c "$p" studio_primer.md)" "$p"; done | awk -F'\t' '$1==0{print "ZERO: "$2; bad=1} END{exit bad}' && echo "OK - manifest"

# reverse check: every token enum that maps to a style_guide field exists in the schema (craft-only groups are exempt);
# also: §2 heading count matches CLAUDE.md, no "separate style reference" clause anywhere, §0.5 REGEN row cites §4
ruby -ryaml -e 'allowed = File.read("schema/style_guide.schema.yaml").scan(/enum: \[([^\]]*)\]/).flatten.flat_map { |l| l.split(",").map(&:strip) }.uniq; exempt = %w[form_proportions color_treatment lighting_extra pixel_art sheet canvas_orientation gameplay_scene object_size_class layout_reference_lock context_starter color_lock character_identity_lock character_sheet ui_kit_sheet negative_map katya_line_removal katya_general_negatives]; ok = lambda { |k| allowed.include?(k) || allowed.include?(k.sub(/\A[a-z]+_/, "")) }; bad = []; Dir.glob("style_tokens/*.yaml").each { |f| YAML.safe_load(File.read(f)).each { |g, vals| next if g.start_with?("_") || exempt.include?(g) || g.start_with?("negative_tail") || !vals.is_a?(Hash); vals.each_key { |k| next if k.to_s.start_with?("_"); v = vals[k]; if v.is_a?(Hash) && v.key?("phrase") then bad << "#{File.basename(f)}:#{g}.#{k}" unless ok.call(k.to_s) || %w[true false].include?(k.to_s) || k.to_s.start_with?("enabled") elsif v.is_a?(Hash) then v.each_key { |kk| next if kk.to_s.start_with?("_") || !v[kk].is_a?(Hash) || !v[kk].key?("phrase"); bad << "#{File.basename(f)}:#{g}.#{k}.#{kk}" unless ok.call(kk.to_s) } end } } }; if bad.empty? then puts "OK - every token enum exists in the schema" else puts "TOKEN-ONLY ENUMS: #{bad.join(", ")}"; exit 1 end'
test "$(grep -c '^### ' studio_primer.md)" = 41 && echo "OK - 41 §2 headings"
! grep -n "separate style / color" studio_primer.md style_tokens/*.yaml && echo "OK - no separate-style-ref clause"
grep -q '`REGEN` / `TWEAK:` | §4' studio_primer.md && echo "OK - REGEN/TWEAK row cites §4"
```
